# Publish vault tools when a labeled PR merges to `main`

## Maintainer workflow

In the GitHub PR sidebar under **Labels**, add `publish-container` before merging to `main`. Remove the label before merging to cancel the request. After a labeled PR merges, GitHub Actions builds the image from the commit that landed on `main`. Applying the label by itself starts no image build.

## What changed

PR #181 removed `push.branches: [main]` from the GHCR workflow and removed its `latest` and `sha-*` rules for default-branch builds. Before that, a merge into `main` ran the container startup smoke test, built for Linux amd64 and arm64, and published both tags. The workflow still publishes on `v*` tags. The Docker metadata action also updates `latest` for a stable SemVer release. [PR #181](https://github.com/tleyden/brain3/pull/181), [Docker metadata tag rules](https://github.com/docker/metadata-action/blob/v6/README.md#latest-tag)

The dependency merge `584523e` passed CI, E2E, and CodeQL on its PR head. Its squash commit on `main` did not run the publisher. GHCR `latest` still reports `a5e2e1b` on both architectures, and `v0.2.12` reports the older release commit `2ae73f2`. The `ci-*` tag requests tests and CodeQL and has no container publishing trigger. [Last publish from `main`](https://github.com/tleyden/brain3/actions/runs/45811117452)

Brain3 normally selects the image tag that matches its gateway version. A one-time `--container-tag latest` selects the moving alias. The official `latest` value in existing configuration is remapped to the release version. Brain3 pulls only when its selected tag is missing locally, so a restart alone can reuse a cached image.

## Restore the publish path

1. Create the `publish-container` repository label. In `.github/workflows/container.yml`, use the `pull_request_target` `closed` event for PRs targeting `main`. Gate the publish job on both `merged == true` and `publish-container` being present in the merge event. This lets an approved merge from a fork publish with the base repository’s package permissions. Unlabeled merges and PRs closed without merging skip the job before a runner starts. Keep `ci-*`, `run-e2e-test`, and `v*` for their existing jobs. [GitHub merge event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#running-your-pull_request_target-workflow-when-a-pull-request-merges)
2. Check out the trusted base branch and verify the event’s `merge_commit_sha` is a commit contained in `origin/main` before registry login or build. Build from that exact commit with the existing startup smoke test and multi-platform build. Use the verified checkout for the OCI revision and publish `sha-<full commit SHA>`. The publishing job uses merged `main` source exclusively, including for fork PRs. Keep the existing `v*` release path and SemVer aliases. [GitHub security guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target), [Merge commit SHA](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request)
3. After pushing the commit-specific image, compare the merged SHA with the current `main` tip before updating `latest` from the published multi-platform digest. If `main` has advanced, keep the commit-specific image and report that promotion was skipped. Show the tag, commit, digest, and promotion outcome in the workflow summary. Stable version releases can still move `latest`, so document it as a convenience alias. [Registry manifest promotion](https://docs.docker.com/reference/cli/docker/buildx/imagetools/create/)
4. Document the PR label and merge behavior in the README and contributor instructions. Explain how to use `B3_CONTAINER_IMAGE_TAG` to select a commit-specific tag or release version. Document that the explicit `--container-tag latest` override needs a fresh pull when the moving tag is cached.

## Verify before using it in production

- Lint the workflow and check the trigger matrix. A labeled PR merged into `main` runs one container publish. Adding the label, closing without merging, merging after removing the label, and direct pushes to `main` start no container build. A `ci-*` tag schedules CI and CodeQL, the `run-e2e-test` label schedules E2E, and a `v*` tag publishes a binary release and versioned image. An invalid merge SHA fails before the build.
- After the workflow is on `main`, add `publish-container` to a subsequent PR and squash-merge it. Verify that the smoke step passed and GHCR advertises both Linux architectures with the squash commit’s OCI revision. Confirm the commit-specific tag and `latest` resolve to the same index digest when promotion succeeds. Run Linux container verification on GitHub Actions.
- The merge trigger applies to future PRs. For the already-merged dependency update in #180, use the existing versioned release path to publish the matching production artifacts.
- For the dependency deployment, both the Rust gateway and Python vault tools changed. A versioned release such as `v0.2.13` supplies a signed Linux gateway and a matching image. If deploying from a source checkout, pair the gateway built from the selected `main` commit with that commit’s published image. Resolve the Hetzner SSH target and verify the active production systemd unit, its configuration path, and the current binary and image before a rollout. Pull the exact published tag, verify its digest, and retain the previous binary and image for rollback. Restart the gateway under systemd and check public HTTPS health, OAuth discovery, and an authenticated read-only MCP call.
